# Building Hard Eng

These instructions apply only to work on this source repository. Do not install this file into target projects. Read `AGENTS.md` for the shared engineering rules; the rules below govern this rebuild.

- Before adding files, dependencies or machinery, state the current requirement and why the existing code or a direct command is insufficient. Keep each implementation minimal.
- Skill creation and revision = follow [Writing Great Skills](.agents/skills/writing-great-skills/SKILL.md), including review of existing skill packages. Use it as the authoring guide instead of Skill Creator; leave the bundled Skill Creator package installed.
- Tick a box only after its behavior is implemented and meaningfully verified. Keep external or unsupported acceptance gaps explicit.
- Review the diff for unnecessary additions and report all changes, actual tests and remaining gaps at the end.
- Keep source-repository instructions separate from the scaffold distributed to target projects.
- Do not commit, push, install globally or change other projects without explicit approval.
- Branches: every PR targets `develop`. Only a `develop` → `main` PR releases.
- Before merging `develop` into `main`, after its CI passes, on the maintainer's Mac: `uv run python release_canary.py <develop head SHA> --post-status`. It installs the release in a fresh scaffold for each stack, a greenfield uv project, a pinned public brownfield project and every installed project. Each installed project must pass its update PR check and its full check. Each new project (scaffolds, greenfield, brownfield) must first pass its setup and full check in the public `Canary` workflow (`.github/workflows/canary.yml`, Linux and macOS) on the same SHA; the Mac canary fails at once without that and does not repeat the check. Then on the Mac, one Claude and one Codex session must change it and end with a passing Hard Eng Stop check; installed projects get no agent sessions (maintainer decision, 2026-10-21), because their checks catch release regressions and the new projects prove the agents follow the workflow. The run fails if commit messages, the diff or PR text name a private repository. A failure in project code → fix that project in its own PR and merge it; change Hard Eng only for a fault in Hard Eng's own code. A project that already fails on the current release does not block the merge; fix it the same way. Rerun with `--project OWNER/NAME`, `--kind`, `--target` or `--agent`, then the full run. Installed projects and agent sessions stay on the Mac: installed projects are private, so public CI logs would name them, and checks in their own Actions would spend the maintainer's private Actions minutes (about 5 hours of checks per release); agent sessions need the maintainer's logins, and Codex never runs in the cloud. Each step's log shows its start time and duration, and the run ends with a time summary per stage; start speed changes from those numbers. Results, logs and project names stay on this machine; the `canary` status holds counts only and is the record, so do not commit the result to a plan.
