# Fix the faults of audit round fourteen: a Stop that checks no commit, a mutation report that cannot run, and failures that name no step

Status: Complete

## Outcome + scope

An audit of the released code ran in sealed copies of five real projects and in two areas of new fixtures. Each fault that it reproduced in normal use is fixed here, with a failing test first. A Stop in a checkout with no record of the session checks the commits that are not pushed. The mutation report of a Python package leaves the performance suite out of its test runs. A test gate whose command wrote no JUnit report says so and names the step. A JavaScript package can keep the support files of its browser tests in the folder that its Playwright settings name. A Dart analysis that fails for files that code generation did not make yet names the step and the role `generated`. A changed Dart `part` file brings its library into the first run of a quick check, so the lints of an analyzer plugin see it. A full check with no `--base` writes the pass record, and a Stop also reuses a record whose base is older than its own, so the Stop after such a check runs no check: it took 0.15 s where it took 1.25 s in a small Python fixture, and the audit measured 9 to 17 s for the old Stop in a Flutter fixture. Non-goals: no change to a project of a user, no new gate, no new option, and no fix for a fault that the audit rates as rare.

## Decisions + authorization

Blockers: None.
Handoff: Approval
Authority: Autonomous. On 2026-11-10 the maintainer told the builder to run the audit and fix rounds autonomously and to follow Hard Eng and Learn. On 2026-11-11 the maintainer said that the builder makes the decisions. On 2026-11-12 the maintainer said that each change must give a real gain and follow best practice, with no change that only renames.

1. A fault is fixed here when the audit reproduced it in normal use and a failing test shows it. A fault that the audit rates as rare is recorded, not built.
2. Decision 10 of round thirteen is reversed. That decision made a project move the support files of its browser tests under a folder named `tests`. A move of that kind gives the project no gain: the folder that a Playwright settings file names in `testDir` is the standard place for those files. Hard Eng now reads that setting. The sealed copy of one real project holds 2 such folders and 6 support files; after slice 4 the rule names neither folder there.
3. Only the string form of `testDir` counts (`testDir: "./e2e"`, with one folder name). A computed value is not read; the project then lists the folder or moves it, as today. A named folder is test code only when it holds a code file and each code file in it is test code by itself: a test file by its name, a file that imports the Playwright test package (`@playwright/test`), or a file that the settings file names as `globalSetup` or `globalTeardown`. Application code does not import that package, so a package with `testDir: "./src"` and tests beside its application code keeps `src` as a source. A support file with no such import keeps the folder outside the sources, as today. The first rule of this branch followed relative imports from the tests. Two reviews showed that a test that imports an index file reaches each file of `src`, with or without a guard on file names: no import walk can tell support code from code under test. That rule is gone.
4. The role `generated` stays the contract for the code generation of a package. A quick check that runs each writer gate one time in a new checkout was rejected: in the five sealed copies the writer roles hold 4 application builds, 3 test scripts and 9 boundary scripts. Slice 5 makes the contract known at the point of the failure.
5. The mutation report leaves out the suite that the performance gate of the package names. A project with its own mutmut settings keeps them without change, as today.
6. Recorded, not built: a setup rerun writes a gates file again when a hand edit changed only its layout (rare); a time weight for the shard split (about 20 s of 5 min).
7. A plain full check records the base that it judged from. A Stop reuses a record of its commit when the base of the record is its own base or an ancestor of it: the full check then judged each change that the Stop would judge, and more. The Stop asks Git that one question only when the record holds its commit and another base. The push check keeps its exact match. A plain check of a change that holds a Hard Eng update writes no record: only a check with a base verifies the release of the update. A record whose commit or base is not text is never reused, and the Git question ends its options before the base of the record.
8. A changed `part` file with `part of '<file>';` adds that library file to the first run. A `part of <name>;` directive gives no first run, so the package run decides.
9. Closed with no slice: an auditor reported that a fix commit on the update branch needs a plan because the size line counts the files of the update. A separate run in three fixtures showed no fault: a small code fix on that branch needs no plan and its push passes, and a fix that changes the gates file needs a plan by the rule for that file. Recorded, not built: when the fix leaves a printed setup step open, the size line names a file of the update; the verdict is the same.
