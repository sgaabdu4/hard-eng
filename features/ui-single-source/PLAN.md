# Every screen comes from one design source and one shared library

Status: Complete

## Outcome + scope

Hard Eng's full check makes every project with UI build its screens from one source: `DESIGN.md` front matter, token files that match it, and one shared component library; screens use only that library. Non-goals: no look rules (colours, sizes and fonts stay the project's choice), no new hook work, no new dependency, no folder renames, no waiver, baseline or list of old cases.

### Exemptions

Each comes from a fact in the repository. No setting lists paths; the policy refuses unknown keys.

| Kind | Repository fact | What is exempt | Reason |
|---|---|---|---|
| Generated code | `.gitattributes` marks its exact path `linguist-generated` (a folder mark counts only for a byte copy of a package, as in every whole-project rule) | all UI rules | no person writes it; fix the generator's input |
| Third-party code | `.gitattributes` marks it `linguist-vendored`, or Git ignores it | all UI rules | it is not the project's code |
| Tests and stories | `_is_test` in plans.py, the same rule as today | all UI rules | tests may set raw values to prove the library; they never ship |
| Token files | `is_theme_path`, the same rule as today, or a stylesheet that holds only custom properties (in `:root` or `@theme` blocks, plus `@import` lines) | raw values | holding values is their job; the `DESIGN.md` compare checks them instead |
| Library files | inside `shipping.ui_library` | base elements | the library is the one place that wraps them; raw values are still refused |
| Email templates | a script file imports `@react-email/` or `mjml` in a statement that starts a line (`import … from '…'`, or `const x = require('…')` or `const x = await import('…')`) and the bound name appears again in the code once comments are cut (a string that holds the name counts as a use); a mention in a comment or a string only, a side-effect `import '…'`, a type-only import and an import whose name is never used do not count; or the file is a `.mjml` file, or is an `.html` file in a folder named `email`, `emails`, `mail` or `mails` | base elements; literal values only when each equals a token-file value, compared as values (28px equals 1.75rem) | about 45% of email clients do not read CSS variables, and they cannot run app components |
| Standalone pages | a `.ts` or `.js` file whose text holds `<!doctype html` | literal values only when each equals a token-file value, compared as values in px (rem and em are 16 px, pt is 4/3 px); base elements are not exempt (the library can hold parts that return HTML text) | served outside the app bundle, so they cannot load the token stylesheet |
| PDF builders | a Dart file imports `package:pdf/` or `package:printing/`, or a script file imports `@react-pdf/renderer`, `jspdf`, `pdfmake` or `pdf-lib` in one of the statement forms above with the bound name appearing again in the code once comments are cut (a string that holds the name counts as a use); a mention in a comment, a string only, a stylesheet or HTML does not count; for Dart, an `import` line of the package that starts a line is enough | all UI rules | a fixed print page in points, drawn with the PDF library's own parts, not screen controls |
| Comment lines and Hard Eng folders | block comments cut from the text with their line breaks kept (a `//` line is matched first), whole `//` lines, and `.hooks/`, `.agents/`, `.claude/` | all UI rules | the same as every whole-project rule today |

Decisions:

Colours, lengths and font families must match both ways as value sets: each `DESIGN.md` value is in a token file, and each token-file value is in `DESIGN.md` (lengths: rem times 16, Dart logical px; Dart doubles below 1 are opacities, not lengths, and are skipped). ## Risks + recovery

Open doubts (no advisor was available; these replace that review):
- The counts come from a regex draft. A sample found one false hex in a text string; other kinds were not sampled. Recovery: slice 2 reruns the real check on every sealed copy, and the rollout table takes those counts.
- The colour compare checks values, not meanings, so two swapped colours with different names pass. It stays judgement in the gate table.
- The Flutter lint plugin will read `hard-eng.gates.json`. A project without Hard Eng keeps the plugin's old defaults, so the plugin stays usable alone.
- The theme-file rule has Dart code in another repository. The cases live once, in the Flutter skill repository, but each tool pins its own revision of it. If one pin moves and the other does not, a project could get two answers. Recovery: a case change ships with both pin moves in one release step; Hard Eng's test and the plugin's test each fail on a case their code does not meet.
- Standalone pages are found by `<!doctype html` in a string. An agent could add that text to a file to get its literals judged against token values instead of refused. The gain is small: literals must still equal token values, and base elements are still refused. A page built without that text is judged as a normal file, which is stricter.
- In Flutter projects the new lint rules run in `check --quick`, so the Stop path does more work there. The settled decision puts Dart checks in the plugin; Verification times it on one Flutter sealed copy, and any added time is fixed in the plugin before its release. If it cannot reach zero, the coordinator decides before the release.
- The UI quality plan's row names cited here come from its builder's working copy on 2026-11-17, which was not yet committed. If that builder renames a row, the citation here is updated in step 1.
- Strict base-element rules may force small wrappers (hidden inputs, file inputs). The research warns against wrappers made too early. The rule stays; slice 2 counts these on the sealed copies.
- The largest fixes (P25: 2,957 items; P28: 1,125; P21: 801) are long. While a project's fix is open, its Hard Eng update stays open, so other Hard Eng fixes wait in that project. Recovery: fix PRs may merge before the release, proven with the release candidate; a later raw value is fixed in a small follow-up fix PR before the update merges.
- Tailwind default palette: a project could define every default colour in its theme to pass. The `DESIGN.md` compare then needs each of them in `DESIGN.md`, and a palette name from `tailwind.config.*` is its path of nested keys down to a leaf that holds a literal colour (`blue-50`; one shade does not define the others), and references and comments define nothing, so the escape closes.
- Stated limits found by the fourth challenge: a `pdf-lib` re-export through another module is not seen as an import; P24's `typography.family` string is a family only per role; the point trap: a theme that holds `pt` values for a print page reads them as screen lengths; Tailwind config values built by a function, and colour groups such as `backgroundColor`, are not read; a few rare comment forms (a comment opener inside a regular expression or a nested template) can still hide or show a line.
- Stated limits found by the second challenge: a library that holds screens takes several visible lines (a part in the index for each screen); colours built from strings (`'#' + 'ff0000'`) are not read; raw values in `.ts` and `.js` files outside `ui_paths` are not judged and token files there are not compared; the generated mark of `.gitattributes` is shared by every whole-project rule, and folder marks are closed by the strict-rules task b2; the no-UI guard was tried on synthetic inputs and on six real no-UI copies, and a server `.ts` with generics and an `<br/>` string, or an `import UIKit` helper, counts as UI.
- Plain JavaScript libraries (P7) export helpers too, so the index may list helpers. Recovery: the builder for P7 keeps helpers out of the library folder.
- Several projects keep tokens inside large stylesheets mixed with rules. They move the token block into its own stylesheet; a stylesheet with only custom properties is a token file whatever its name, so no rename is needed. The move separates the values (layer 3) from their users, which is the layer split the brief settled.
- An empty `ui_paths` with only mockups or docs pages in `.html` triggers the no-UI guard, because the guard counts `.html` as UI source as the user's decision asks. None of the 6 projects with empty `ui_paths` has one today.
