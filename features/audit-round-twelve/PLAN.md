# Make hook events faster, refuse shard settings that the merge cannot follow, and fix the faults of audit round twelve

Status: Complete

## Outcome + scope

Each hook event and each command starts faster: the hook script is a small launcher, a clean event loads only the modules that it uses, and its slow reads run at the same time. A shard gate refuses a test path in the pytest settings, and each option or variable that moves the settings of pytest or coverage.py, so the merge cannot skip a project's own coverage minimum. An audit of the released code then ran in sealed copies of five real projects and in two areas of new behavior, and each fault that it reproduced in normal use has a slice in this plan. Non-goals: a time weight for the shard split; reuse of a passed manual quick check at the next Stop; a deal of files to shards that moves few files after an edit; a copy check of JavaScript, Dart and Swift test files; a settings load with no Git start for attributes (measured and rejected, see Decisions).

## Decisions + authorization

Blockers: None.
Handoff: Approval
Authority: Autonomous. On 2026-11-10 the maintainer told the builder to run the audit and fix rounds autonomously and to follow Hard Eng and Learn. On 2026-11-11 the maintainer said that speed is important, that each change is timed old against new, and that the builder makes the decisions.

Decided:

1. The path `.hooks/hard-eng.py` does not change. Each hook, workflow, Git hook and installed step names it.
2. The launcher keeps the syntax of Python 3.9 and loads no other file before the floor check, so an old `python3` still gets the plain refusal.
3. The launcher starts the module only when it runs as a program. A load of the launcher as a module runs nothing; each test that needs the functions loads `gate_runner`.
4. A shard gate refuses a moved setting; it does not read it. A reader would copy more of pytest, pytest-cov and coverage.py, and each allowed value would need a comparison with the real tools. The refused set: `-c` and `--config-file`, `-o addopts` and `--override-ini addopts`, `--cov-config`, `--cov-precision`, and the variables `PYTEST_ADDOPTS` and `COVERAGE_RCFILE` when they are not empty. Each one has its own printed step. Local count on 2026-11-12: none of 40 checkouts uses one of them.
5. A test path in `addopts` is refused with the same text as a path in the command, and the text names the settings file.
6. No settings load without the Git attribute lookup. Measured on this repository: the lookup takes 9.5 ms, of which 7.1 ms is the Git start. A skip is correct only when no attribute source exists, and Git has at least five: a `.gitattributes` file in each folder, the index, `info/attributes` of the common folder, the file that `core.attributesFile` names, and a system file whose path depends on the Git build. A wrong skip changes which files count as generated.
7. No change to the shard split in this plan. Three reviews read it in round eleven. In the CI run of the round eleven release, five of the six parts took 21 to 82 s and one took 157 s, because that part holds the test files that run real tools. File size is a weak weight, but a time weight needs stored data.
8. A hook module loads `hashlib`, `tempfile`, `urllib.request`, the update code and the cleanup of update leftovers inside the function that uses them. Each other import stays at the top of its file. A session start keeps `tempfile` and `shutil`, because the attribute lookup of the settings load needs a temporary file.
9. Reads that run at the same time use one plain thread each, through `background`. No pool and no async code. The caller gets the same error that the direct call gave, for each error class that its handler names.
10. The merge judges the coverage minimum by the coverage.py release that the shard reports name. A report with no release gets the rule from before 7.17.1.
11. A drain loop passes only in its exact form: the condition reads one collection, the body is one statement, and that statement waits for all work of the same collection. The wait takes the collection itself, a list copy of it or a spread of it; each other argument stays a finding, so a loop that takes one item for each pass does not pass. Two awaits of futures that already run stay a finding: the record form passes, is shorter, and is the step that the message names.
12. `test_driver` is test code. `bin`, `tool` and `scripts` stay code that a project lists as sources. A gates file that already lists `test_driver` keeps passing.
13. The setup plan is kept only at the two proof call sites, in the scopes that `check` already opens: the plan of the working tree until the gates start, the plan of the base commit for the whole check. `update_plan` itself keeps nothing, because install and repair call it.
14. The pub upgrade step uses `--unlock-transitive`, which needs Dart 3.6 or later.
15. Recorded and not built, each with its reason: reuse of a passed manual quick check at Stop (the Stop record belongs to a session and holds file hashes that a manual check does not make); a clear text for a setup rerun whose recorded release the source no longer holds, and for a failed fetch of a pinned skill commit (both rare); `update-pr` with no shipping block on the base (rare); a plain `check --quick` with no base checks each package, as its help text says; a shard gate does not see `-c` inside a group of short options such as `-qc` (rare); a retry count of zero on the line after its option, in a list with one item on each line, is refused, and the one-line form passes (rare).

## Risks + recovery

- An installed project updates from a release with the long script. Its update copies each hook file, so the launcher and the two new modules arrive together. Recovery: the update test of slice 1, the sealed update proof in Verification, and the canary's update project, which installs the last release and updates to the candidate.
- A pushed revision older than the launcher has its options in the script. Recovery: the push check reads both files of the pushed revision; the second push check test proves the old form.
- A tool or a person loads `.hooks/hard-eng.py` by path for its functions. Recovery: decision 3 makes such a load run nothing; the functions are in `gate_runner`.
- A project already uses a refused option on its shard gate. Recovery: the refusal names the option and the step for that option (a settings file that the tool reads with no option, or the tests command), or the removal of the `shards` field; the local count found no such project.
- A later edit puts an unused import back on the path of a hook event. Recovery: the test of slice 4 fails and names the module.
- A thread in a hook event hides an error or leaves work behind. Recovery: `background` gives the named error to the caller, each caller waits for its thread before it returns, and the whole output of each event was compared old against new.
- A kept setup plan is stale. Recovery: the plan of the working tree is kept only until the gates start, in the scope that already keeps the file listings; the key holds each argument; with no open scope each call computes again.
- A project on a Dart release before 3.6 gets a pub upgrade step that its tool refuses. Recovery: none in this plan; each local project runs the current stable release, and the refusal of the tool names the unknown option.
- `.hooks/plans.py` is at the line limit. Recovery: the next change to it moves code to an owner first.
