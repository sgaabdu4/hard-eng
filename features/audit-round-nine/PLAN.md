# Enforce the UX rules by script, make the push check faster, test the PR text in CI, and fix the faults of the round 9 audit

Status: Complete

## Outcome + scope

A brief for a design carries the full Usability list, and a UX record holds one Pass or Fail line for each Usability rule. `check` refuses a record that skips a rule, and a record that claims a pass while a rule fails. Two marks of careless UI code are refused in the added lines of a change: a transition on every property, and a colour literal outside a theme or token file. The design file template states the basics of hierarchy, motion and states. A push does not repeat a full check that passed on the same tree. The PR text rule runs in CI for each PR. Added lines that turn on test retries are refused. An update canary proves the update flow in CI. Each fault that the round 9 audit reproduced in normal use gets a fix.

On 2026-11-11 the maintainer added one more outcome: each PR that Hard Eng ships has a short and clear text. The form rule asks for a summary first and folded detail, and `ship` and the CI job refuse a wall of text.

The bar for this round is the bar of round 8: build a fix for a wrong pass, a wrong fail, a printed step that fails, a state with no way out, or a slower hook or check.

The round 9 audit ran five auditors in sealed copies of the released code. Two of them used four real public projects: a Python library on Poetry, a TypeScript library on Bun, and two workspaces. One auditor (a new project and its daily tasks, on two agent clients) found no fault. The other four reproduced faults in normal use. This plan fixes the ones with a clear fix at an owner that this plan already changes: the Poetry and Bun freshness steps, the vulnerabilities gate with a dynamic version, the skip forms, the empty reason, the commented-out test, the missing lockfile message and the tilde fences. The others need designs of their own and are named in the non-goals.

Non-goals:

- UI rules that were judged and not built. A ban on ease-in curves: Material motion uses an accelerating curve for an element that leaves. A ban on a start scale of zero, a flat duration limit and a ban on animated size properties: the source of these ideas breaks each one in its own approved samples. A quoted colour in TypeScript: charts, social card images and email renderers need a plain value; the Tailwind forms and the Dart and Swift forms are the clear cases. A disabled zoom and filler text: no hit in 12,183 UI files of 39 projects. A reduced-motion test for each package: it proves little.
- Tests on the running app (a platform accessibility audit, worst-case data, text at 200%): the next plan, after a run on real end-to-end suites.
- A hook that reads subagent briefs: the word "design" has many meanings, and one of the two supported agent clients has no such hook. The rule is text, and the `Rules` field is the script check.
- Open faults for the next plan, each reproduced before this round: the findings of four tools cannot become adoption debt, so one real Dart package cannot finish `adopt`; the comment rule makes a small fix clean each old comment block of the file; a false positive of the secret scan in bundled output has no way out. Also for the next plan: settings forms that weaken a check, and the smaller speed items of the round 8 list.
- The split of the CI tests over shard jobs: the next PR, alone (Decided (18)).
- The update flow got no auditor of its own in this round. The update canary of this plan runs that flow in CI.
- Audit faults for the next plan, each reproduced: a plan test that the test run never collects still passes Complete; the mutation run of the push includes performance tests with a time budget; cleanup of a task that was built in the main checkout ends in a circle of refusals; and the adoption of two real workspaces stops at Dart language flags from an included lint package, at a nested package inside an analyzer run, at a coverage list wider than the project's own, and at member gates that name a missing tests folder. Their designs started in this round.

## Decisions + authorization

Blockers: None.
Handoff: Approval
Authority: Autonomous. On 2026-11-10 the maintainer told the builder to run the audit and fix rounds autonomously and to follow Hard Eng and Learn. On 2026-11-11 the maintainer approved the build of the items from the study of another project's CI and PR practices, asked for one PR with parallel builders, gave the UX rule change as a written request with four numbered parts, asked that UI rules be enforced by a script where possible, and gave a list of standing UX rules with "no clutter" and "clear visual hierarchy" as the two that matter most.
Decided (1): the Usability list has 13 rules, each with a label. Three are new or stronger: `Observe`, `No clutter` and `Hierarchy`; the old "Calm screens" rule is now inside the last two. A touch target is at least 44 px (48 dp on Android), by the maintainer's list; 24 px stays the floor for a control that only a pointer uses.
Decided (2): the labels have one owner, the reference file. The plan check reads them from that file at the moment of need, so the code holds no second list. A label with a count marker asks for a number before each unit word of the marker in its Pass line: `(count: clicks)` for `Least effort`, `(count: kept, removed)` for `No clutter`. The unit words live in the reference file too.
Decided (3): a `Rules` line says Pass, Fail or not applicable, each with its text; the not-applicable form is the one that plans already use, with a reason. A rule that does not apply to a design (no time shown, no staff role) says so; without that form an agent would write a false pass.
Decided (4): `Rules` is needed in each Draft or Ready plan with a passed UX record, old or new. Its design is still open, the refusal names a step that works, and the check adds no Git start. Of 1,397 plans in 39 local projects, one Draft plan must add the lines. A Complete plan that changed against the base passes without the field when nobody touched it since the last Hard Eng update of its project, so an update alone turns no finished plan red. The check reads the age of such a plan one time. A plan that holds the field is always judged. An unchanged Complete plan is not judged at all. The refusal names the step and shows the form of a line.
Decided (5): the script check for UI source judges only added lines, as the switch-off guard does, so no installed project fails for old code. A change with no UI file pays one suffix test for each changed file. A colour is free in a file whose folder name, or the last word of whose file name, is a theme word (`theme`, `token`, `color`, `colour`, `palette`, each also in the plural), and in the Tailwind config file; a project needs no new setting, and the step of the refusal can always be done.
Decided (6): the design file template gets three sections (`Hierarchy`, `Motion`, `States`) and two longer prompts. No check requires the new sections, so no existing design file fails.
Decided (8): the PR text rule gets one owner, the new `.hooks/pr_text.py`, which `ship` and a new CI job both call. The job `pr text` reads the PR text from the event file, never inside a shell line, and runs again on each push and each edit. It tests each PR to the shipping base, drafts and forks too. It skips the generated Hard Eng update PR, which never passes through `ship`, and a PR to another base, such as the release PR. Installed projects get the job with their next update. A run of the tests that a plan names on the merge base was judged and is not built: a plan has no mark for a bug fix, and a test that cannot be collected on the base looks like a failing test in three of the four languages.
Decided (9): each PR text holds a `Not checked:` line that says what no check covered, so that a reader does not take silence as coverage. A bare "none" is refused; "None" with a reason passes. An open PR of an installed project meets this at its next `ship --stage ready`, and the refusal shows the line to add.
Decided (10): the update canary is one more target of `release_canary.py`, on Linux, with the Python fixture. It installs the release at the merge base of the candidate and `main`, updates with the project's own installed updater from a local copy of the source, and runs the full check on the update branch. The release gate waits for it. It cannot prove the PR half of an update, the setup rerun or the session start path; so it would not have caught the two update faults of round 8, which slice 5 fixes with their own tests. A flow for the setup rerun is for the next plan.
Decided (11): a size number for a project's own rule text is not built. A project can cap its rules today with its own test and the `impact_inputs` field, as Hard Eng does for the shared block.
Decided (12): the known faults of the update flow get the fixes that the round 8 research designed. A repair branch in its own worktree is ready when nothing is newer. A setup rerun prints the "CI setup pending" step at most one time, and not at all when the checkout already holds the shipping block. A failed update proof names its reason one time, and a failed fetch is tried one time for each run. A missing coverage report names the `--cov=` step. The dependency gate leaves out a Sphinx `docs/` folder that is not in the sources.
Decided (13): three printed steps are repaired. The imports gate names the build system step for code under `src/` with no build system. The debt refusal names a step that a test takes when the base branch is not on a remote yet, also when the install is the only commit; with a detached head or on another branch it names the switch to the base branch first, and it prints no step that moves a ref there. A Flutter project that does not list `test` is not told to use `package:test`. A fourth item is not built: entry points of the dead-code gate for a Dart app. A run of the real tool on the Flutter starter showed that a written entry list replaces the tool's default entries, so each test file is then reported as dead. A dead file under `lib/` of a Dart app still passes that gate; the fix needs an option of the tool that adds to its defaults.
Decided (14): a push does not repeat a full check that just passed. A full check with a base, with no language filter and no quick mode, on a clean tree, writes a pass record in the Git folder of its own worktree: the commit, the base commit and the start time. The push check is spared only when the pushed commit and the base are the recorded ones and the record is at most 30 minutes old; any other state runs the push check as before. A check that starts removes the old record, so a failed check leaves none. A partial check and a check in CI do no record work, because no push can read their record. CI still runs the full check on a clean clone before each merge; that covers a pass that depended on an ignored local file. The push check also reads the shipping policy from the pushed commit, keeps the Git settings of the push for its snapshot, and accepts a lockfile that is a tracked symbolic link.
Decided (15): the vulnerabilities gate accepts a package with no version only when the uv lockfile marks it as local (an `editable`, `virtual` or `directory` source). Two auditors met the old refusal in real projects with a dynamic version; the project could not end it, and the line named no package.
Decided (16): an added test retry is refused by the switch-off guard, judged by file kind: test files, test config files, the gates file, package scripts and Xcode test plans. Production code is never judged: the word "retry" stands on 142 production lines of two real copies. A zero retry passes. The patterns load only when an added line holds a retry word, so a change without one compiles nothing new at Stop. The first draft of the pattern hit four false lines in one real test file; the final patterns hit none in 603 real test and settings files. Rules for sleeps and clock reads in tests are not built: in four real copies they are mostly correct uses. The same guard now refuses four skip forms that two auditors got past it: a raised `SkipTest`, `skip` imported by name, a skip method used as a value, and an indented `__test__ = False`. The Semgrep timeout message names each file and the step. Two ideas need no code: each reader of an empty report already refuses or passes by design, and a fixed debt line already asks for `adopt`.
Decided (17): the freshness gate names only a version that its printed step installs. For Bun, the step carries the gate's two-day release wait, and peer rows are skipped: a peer range is the package's contract with its users, and no Bun step widens one. For Poetry, the target is the version that Poetry's own solver picks in a dry run with the project's Python range, its pins and the release wait; the step names the section of each dependency and keeps its extras and markers. A dependency that cannot move gets a note with the command that shows the cause, and does not fail. A probe with the real tool (Poetry 2.5.1) proved the base of the Poetry part before its build: with pytest 7.4.4 installed and 9.2.0 as the latest, the dry run named 8.4.2, the newest version that installs with the project's Python range. A scanner refusal names its gate and command.
Decided (18): the split of Hard Eng's CI tests over shard jobs is not in this change. Its runner half is built on its own branch. It rewrites the required CI workflow, so it ships alone in the next PR, where a fault blocks only itself.
Decided (19): on 2026-11-11 the maintainer reported that a collaborator's two PRs skipped Hard Eng in an installed project: the push hook was not active in the fresh clone, the CI check waited with no runner, a stacked PR got no check, and the default branch did not require the check. The code shows two different causes than the report names: Hard Eng never sets the hooks path of Git, and its own workflow already runs for a PR into any branch; the branch filter was in the project's own workflow. Only a required check on the default branch stops a person who skips setup or pushes with the hook off, so that is the control that Hard Eng now names. `ship --stage ready` and `merge` print a warning when the base branch does not require each shipping check, with the settings page where an admin adds it, and a "Not checked" line when the rules cannot be read; it is never a refusal, because some repository plans cannot require a check. A required check that no runner has taken for longer than the CI budget is named with its runner labels. Setup names a project workflow that runs the check only for PRs into some branches. The README says that a fresh clone pushes unchecked until setup runs, and that each PR's job goes to the configured runner, whoever opened it. Not built: a package install script that sets the hooks path (it helps one stack, runs in each container build, and the hook can still be skipped), and a paid hosted runner for people whom a self-hosted runner refuses (the maintainer's choice).
Decided (20): a removed line of a test file keeps a change big unless it is an import line or an empty line. An edited import line made a two-line fix need a plan. A wider rule (any line that holds no check) is not built: the reader of assertion lines misses forms such as `with pytest.raises(`, so it would let a removed check pass as small. The README now says that a big change with no plan stops `check` before any gate.
Decided (21): on 2026-11-11 the maintainer said that the PR texts are long, hard to read and with no visual order; the text of the round 8 PR had 39,771 characters. The PR text rule now asks for a summary first, one line for each main change and folded detail. The check refuses more than 6,000 visible characters, and a visible line over 600. Code blocks, folded blocks, HTML comments and link targets do not count. Measured on the last 120 merged PR texts of this repository: the visible size has a median of 1,046 characters, none is between 5,000 and 8,000, and 8 are over 8,000. Measured on 1,053 PR texts of 34 local repositories: the limits refuse 30 texts, for 22 long paragraphs, 12 long list items and 9 long undo lines; one of the 30 is bot-made. An undo line for more than 5 commits gives the count and the subjects of the newest and the oldest commit. The CI check skips a PR that Dependabot or Renovate opened, because a bot writes that text: 79 of the 1,053 texts are bot-made, in 10 repositories. A check of the sentence length is not built: tables, names and code make a word count wrong too often.
Decided (22): a Draft plan with a clarification handoff is not judged for `Rules`. The third outside review of the UX rules named this. No part of a UX record is judged at a clarification handoff, on the base branch too, because a design is shown at the approval handoff, and that handoff is judged.
Decided (23): the hook timing found a cost of the five new modules. Each config load walks each listed file, so five more files gave 1,892 more Python calls in one load: 66,903 on the base and 68,795 with this change. The file list now asks the file system one time for each name; before, it asked two times and built each path three times. One load now makes 63,798 calls, which is below the base. The list is the same: a symlink, a missing file and a folder stay out.
Decided (7): room first. The requirement registry moved out of `.hooks/plans.py` (1,000 lines, now 826), and the Dart-only checks moved out of `.hooks/hard-eng.py` (997, now 870). The import of `plans` builds 39 patterns, 46 before.
