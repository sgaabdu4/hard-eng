Status: Draft

## Outcome + scope

### Why Hard Eng did not enforce this

- The plan check validates fields, not truth. The builder typed one Pass line per rule; nothing compared a line with an image.
- `ux_reference: N/A — <reason>` passed with any reason. The check never looked at the diff, so a removal of two buttons from a screen file passed as nonvisual.
- The ship check proves an attachment is an image. It does not measure the screen or prove that anyone opened it.
- The code-review "Visible change" line is skill prose. No command records it, so no gate can ask for it. The independent review gets the diff and the plan with its Pass lines, and no images.
- `browser capture` only takes pictures, at 2 widths. It measures nothing.
- Alignment, spacing and design-system match were not named rules.

## Decisions + authorization

Blockers: None
Handoff: Approval
Authority: Human-loop. The user said yes to planning these additions through the coordinator on 2026-11-16 ("please plan the two Hard Eng UI additions you named"); the user has not yet seen this plan. This is a plan-only run: the build, the Flutter lint plugin PR and the release wait for the user's approval of this plan.
Decisions:

1. Measurement runs inside `browser capture`, before its page script changes the page, at each width. It writes `<name>-<width>.json` next to each image, with the image's SHA-256, the findings, the commit it was taken from and whether the checkout had uncommitted changes. A capture with findings still keeps its images, because a before image of an old screen may fail.
2. `ship ready` and `ship merge` refuse a PR with Before and After pairs unless each After attachment has the same SHA-256 as a measured capture with no findings, in the checkout's `.hard-eng/browser/`. So a plain screenshot or an image from elsewhere cannot stand as an After image. A Flutter or Swift After image needs no measured record when every visible changed file is in a Flutter or Swift package. For each After name, records must exist at all 3 widths. A state reached by clicks gets the same proof: a new step `browser measure --session S --name NAME [--ring SELECTOR]` measures the open session's page at its current width, draws the rings, takes the screenshot and writes the same record. The agent runs it once at each width. A ring drawn on an image afterwards changes its bytes, so an After image must take its rings from `--ring`; checks.md says so.
3. A changed Flutter screen file needs a widget test that imports it and calls `meetsGuideline` with `textContrastGuideline`, `labeledTapTargetGuideline`, `iOSTapTargetGuideline` and `androidTapTargetGuideline`. `ship` checks this from the files; CI cannot, because its job checks out only `.hooks`. The test itself runs in the project's tests gate.
4. A new command `python3 .hooks/hard-eng.py look <image>...` runs the fresh review. It copies the images into an empty temporary folder and gives the reviewer only those images and the Usability rules. It never names the repository, the plan, the diff or the builder's lines. Limit: this is isolation by prompt and folder only. The reviewer can still read other files: in the spike, the Codex reviewer ran a shell command that read files outside its folder, and a Claude `Read` tool reads any path. The reviewer gives one `- <rule>: Pass|Fail|N/A — text` line per rule, one `Image <name>: <detail>` line per image and a verdict.
5. `look` proves the reviewer opened each image. Claude: the `--output-format stream-json` stream holds a `Read` call of each image path with an `image` result. Codex: the `exec --json` stream gives the thread ID on its first line, and the session file `sessions/YYYY/MM/DD/rollout-*-<thread>.jsonl` holds an `ImageView` item for each path. An image with no read is `not done`, and `ship` refuses `not done`.
6. `look` records at the Git path `hard-eng/look/<head>.json`: image hashes, read times, the rule lines and the verdict. The PR body carries the rule lines in a `Look review:` block. CI `pr text` refuses a PR with pairs and no block with one line per rule and no Fail. The block also lists the SHA-256 of each image the reviewer opened, and CI downloads each After attachment and refuses a hash that the block does not list, so a block typed without `look` fails CI unless someone copies hashes by hand. `ship` compares the block with the record. The CI job checks out only `.hooks` and gets file names from the PR files API, so it reads changed lines from each file's `patch` field (a file with no patch, such as a binary or a very large diff, counts as visible) and reads the changed PLAN.md text from the API at the head commit. The Flutter guideline-test check needs the project's files, so it runs in `ship` only. These look lines are the code-review "Visible change" lines: review.md tells the reviewer to run `look` and copy its lines, so the required lines are the ones a script can tie to opened images.
7. Visible change, for the `ux_reference` refusal. The file matches `ui_paths` and is not a test or generated file. It has a changed line, added or removed, that is not blank or a comment. It is one of these kinds: a markup or style file (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.astro`, `.html`, `.css`, `.scss`, `.less`); an image, font or SVG; a string catalog (`.arb`, or `.json` under `l10n`, `locales`, `i18n` or `messages`); a theme or token file; a Dart file under a Flutter `lib/` that names `Widget` anywhere, or whose changed lines hold a string literal (helper functions and extensions that build widgets count); a Swift file that declares a `View`, `UIView`, `NSView` or view controller type; a `.js` or `.ts` file whose changed lines write to the page (`innerHTML`, `textContent`, `createElement`, a style or class change). Other `.js` and `.ts` files count as logic. Limit: screen text kept in a `.ts` constants file is missed. A string-literal rule was tried on past plans and flagged server route files, so it was dropped. A deleted file of these kinds counts. Anything else in `ui_paths` is not visible: tests, Dart files with no widget and no string, TypeScript logic files, comment-only changes. A visible change whose screen does not change in fact writes one line in `ux_reference`: `N/A — unchanged: ![Before](<file>) ![After](<file>) — <screen and state>`. That line already passes today's plan check, so `plans.py` does not change. `ship` refuses it unless both files are measured captures of the same widths and state with equal bytes, the Before taken at the PR's base commit and the After at its head, each from a clean checkout; CI checks its form. The PR note `UI appearance: unchanged` on a visible change stands only beside that line. So a builder never types "no visible change" without proof. A spike captured the fixed fixture and a public home page twice each: the bytes matched at both widths.
8. The rule changes stay in ux.md, in place. The 30 lines are not appended.
9. Nothing joins the Stop hook path: no change to `plans.validate_plan`, `gate_runner`, or any hook. The new checks run in `browser capture`, `look`, `ship` and the CI `pr text` job.
10. ux.md text, changed in place (each rule stays one short line, per HE-NO-TEXT-WALLS):
    - No clutter: starts "Least cognitive load:" before "for every element ask …".
    - Hierarchy: "… everything else is quieter: one filled button per action group, the rest outlined or text. One focus per screen, at most 2 accent colours per block, labels with one meaning."
    - New Alignment: "the text and controls of one block start on one shared edge; no centred line above left- or right-pushed content."
    - New Spacing: "gaps come from the design system's spacing scale; like items get equal gaps."
    - New Design system: "colours, type, spacing and components come from the `DESIGN.md` tokens and theme owners, and match the nearest existing screens."
    - Messages: "plain, calm and positive words".
    - Accessibility: adds "text at least 14 px; contrast at least WCAG AA".
    - Widths: "phone 390, tablet 768 and desktop 1280 px, plus each other width the app supports; nothing scrolls sideways."
    - The Usability lead line and the last line say that a typed Pass is a record, and name the proof: measured captures, `look` and its session proof.
11. This ships as its own release. It merges to `develop` only after the wider-switch-offs release is on `main`, so the two never share a release.
