# Remove merged, unused branches and idle build folders in the session-start background run

Status: Complete

## Outcome + scope

The background run that each session start already launches also removes merged local branches of the same repository and the idle Rust build folders of the repository's worktrees. It uses no model tokens and adds no hook time. Non-goals: remote branch deletion; a GitHub repository setting change; a new command or agent text; branches and worktrees of other repositories; checkouts with no installed source revision (the Hard Eng source repository and installs from an uncommitted copy), because a launch there would add hook time; Windows hosts for the build folder step; removal of worktrees. Worktree removal is a follow-up on the branch `feature/session-start-tidy-worktrees`: each review found a loss there, and a ref cannot bring back a deleted file.

## Decisions + authorization

Blockers: None.
Handoff: Approval
Authority: Autonomous — the user asked for a deterministic, token-free tidy at the very start of a session; design is the maintainer agent's call. This task is plan-only: commit the plan, no push, no code.

Design, settled:

- Where: `run_update`, after the update lock is released. The tidy takes its own lock, `hard-eng-tidy.lock` in the Git common folder; a held lock → no tidy this run. So `update_running` and the "still running" notes do not change. `start_update` and every hook path stay unchanged, so no hook does new work. The tidy runs when the update child fails, but not after a signal stopped the run. During the tidy, SIGTERM has its default action. A stop between two removals loses nothing: each removal is one command on an item that passed every check.
- Time limits: every Git call 120 s, `lsof` 60 s, each gh call 60 s. One error rule: a command that fails or times out for one item (a branch or a build folder) keeps that item, the log names the command, and the tidy goes on to the next item. A failure that concerns the whole repository (the base fetch, a listing) stops the tidy for that repository and keeps everything not yet removed.
- Report: the tidy prints one line per item, kept or removed with the reason, to the run's output, which is already `.hard-eng/update.log`. Only when it removed something, it adds one line to the result file, which the next session start already prints: `Tidy: removed N branches, N build folders (.hard-eng/update.log).` The line never holds the word `failed`, so the freshness and Stop notes read it as before. Nothing removed → no line, so no tokens.
- Base: `update_base` (shipping base, else origin's default branch), fetched with `fetch_base`. A failed fetch stops the tidy; the log says why.
- Merged: the head is an ancestor of `origin/<base>`; or `git merge-tree --write-tree <tip> <head>` merges cleanly into exactly the tip's tree (the base already holds every change, whitespace included; `git cherry` ignores whitespace, so it is not used). The merge runs in an empty scratch repository with the real objects as alternates, `--attr-source` set to the empty tree, no attributes file, no system or global config and no `info/attributes`, so no merge attribute or merge driver (`merge=ours`, `merge=union`) can turn a change into nothing; no single Git switch covers `info/attributes`, so the scratch repository is the switch; or a PR merged into the base has that exact head commit (`gh pr list --state merged --head <name> --base <base> --json headRefOid`, only when the Git tests fail). A PR merged into another branch never counts.
- GitHub calls: every local check (ancestor, content merge, idle, stash, log, symbolic ref, process) runs before any gh call; gh is last. A gh answer that keeps an item is remembered in the Git common folder (`hard-eng-tidy-gh.json`) for 24 hours: no merged PR for a branch at a head, and an open PR for a branch. A missing or failed answer is not remembered. So a kept branch costs no gh call at the next session start. The tidy lock is in the same common folder, so sibling worktrees never run a tidy at once.
- Objects: `git merge-tree --write-tree` runs with a scratch object folder under the temporary folder (the repository's objects as alternates), so the tidy writes no object into any repository; the folder is removed at the end, and an abandoned one falls to the temporary-folder sweep after a day. A dry run over 123 repositories wrote 23,315 loose objects into 16 of them (20,424 in one) before this rule.
- Logs: each log file is read as bytes and split only at a newline (`str.splitlines` also breaks at form feed and the Unicode line separators, which Git keeps inside a message); a field is accepted only as a full lowercase 40 or 64 character id, else the branch is kept with one log line; the ids go to `git rev-list --stdin`, never as arguments. Other text that reaches a Git command is a ref name from `for-each-ref` (never starts with `-`) or an id that Git printed. Both commit ids of every line in the log file of a branch (the old and the new value; a plain `git gc` keeps both, `git log -g` prints only the new one) are read from the file, a zero id skipped, and every one is checked; a removal drops that log, so a branch stays when any commit in it is neither an ancestor of the tip, of the head or of a remote branch, nor merged by content. The walk uses `git rev-list <commits> --not <excluded>` and keeps the named commits, because `--no-walk` ignores `--not`.
- Open PR: one `git ls-remote --heads origin`. A branch that is still on origin needs `gh pr list --state open --head <name> --json number` (one exact call per branch, so no page limit hides a PR); any open PR keeps it. No gh answer (missing, failed, timed out, not GitHub) → every branch still on origin is kept.
- Rescue refs: the one act that deletes (`Tidy.destroy`) first names the commits that the removal drops by refs `refs/hard-eng/tidy/<UTC time>/<commit>` in the common folder: one ref for each independent tip (`git merge-base --independent`) of the named commits that the base tip lacks, because a ref keeps its ancestors (a squash-merged branch of 40 commits leaves one ref). The refs are written in one `git update-ref --stdin` call (a failed write keeps the item) and are fresh even when an older ref holds the commit, because that ref may expire in this run. Then the checks run again, then the removal record is written, then the branch is deleted. Before any deletion a local branch, remote-tracking ref or tag other than the removed one must hold the base tip that the checks used; if none does (a narrowed fetch refspec such as `--single-branch` writes no `refs/remotes/origin/<base>`), a rescue ref is written at the base tip too (end fixture `base-outside-refspec`). Rescue refs expire after 30 days, the same as the record. Limit: a branch merged by content keeps its intermediate commits only for those 30 days; plain Git keeps them while the branch exists. Git prunes a loose object by its file time, so only a ref keeps a commit across `git gc`. Readers of all refs: the pre-push secret scan rewrites `--log-opts=--all` to `--remotes --tags HEAD`, so it never reads them; the tidy's own walks use `--branches` and `--remotes`; the CI secret scan runs on a fresh clone without them. No reader skips them. A dry run over the largest real repository (72 removable branches) would write 20 rescue refs in one pass.
- Scratch repository: one helper runs every Git command there, `init` included, with an empty template, no system or global config, no attributes and an environment built from `PATH` only. Limit: the scratch repository uses SHA-1, so a SHA-256 repository never detects a squash or rebase merge by content; the merge test fails and the item is kept (fails safe).
- End condition: `tests/test_tidy_end.py` runs 17 fixtures (the reviewers' repros among them). For each, a copy of the repository runs only `git gc --prune=now` as the control; the original runs the tidy and the same collection. A commit that any ref or log named (read as plain files, ORIG_HEAD included) is lost when the control still has it and the tidy copy has not. Every ref that is gone must be named in the removal record, every HEAD must still resolve, and every untracked or ignored file of the main checkout and of each linked one must still exist, except Rust `target/` output with the marker and no nested `.git`. The test imports no guard. The symbolic-branch fixture fails on the revision before the symbolic ref rule.
- Grafts and replace refs: every tidy Git command runs with `GIT_NO_REPLACE_OBJECTS=1`, so `git replace --graft` cannot make an orphan branch look like an ancestor; when `info/grafts` exists in the common folder, every branch is kept and one log line says why (`tests/test_tidy_rules.py::test_tidy_keeps_every_branch_and_says_why_when_info_grafts_exists`; the end test has both graft forms, finished by dropping the graft before the collection).
- Reftable: reflogs are read as plain files, so when `extensions.refstorage` is set to anything but `files` (the config key works on every Git version) every branch is kept and one log line says why (`tests/test_tidy_rules.py::test_tidy_keeps_every_branch_when_the_reflogs_are_not_plain_files`).
- Paused operations: a branch that `rebase-merge/head-name`, `rebase-apply/head-name`, `BISECT_START` or a `refs/heads/` line of `rebase-merge/update-refs` names in any worktree counts as checked out, so a paused rebase or bisect finds its branch.
- Paths: every tidy path comparison (process path, session) folds letter case and Unicode form (NFC) on both sides, because a macOS volume ignores both and `lsof` may spell a path differently.
- Branch config: after a removal the tidy runs `git config --remove-section branch.<name>` unless another local branch or config section name starts with `<name>]` (Git matches the section up to a `]`, so it would remove that section too; `tests/test_tidy_rules.py::test_a_branch_whose_name_ends_the_section_name_of_a_kept_branch_keeps_that_section`), when it skips, the log names a per-key `git config --unset-all` for the removed branch only; a name that holds `]` is never given to `--remove-section` (Git refuses it): the log names per-key `--unset-all` commands, and nothing is logged when the removed branch has no settings of its own (`tests/test_tidy_rules.py::test_a_collision_says_nothing_when_the_removed_branch_has_no_settings`); it logs the command when the section is still there afterwards (`tests/test_tidy_rules.py::test_a_section_that_git_refuses_to_remove_is_reported_with_per_key_commands`), so a later branch of that name picks up no old upstream or description; a failure other than "no such section" (a held `config.lock`) logs the exact, shell-quoted command to run before the name is reused, also when the call times out (`tests/test_tidy_rules.py::test_a_failed_config_cleanup_is_reported_with_a_quoted_command_to_retry`, `tests/test_tidy_rules.py::test_a_removed_branch_takes_its_config_section_with_it`).
- Removal record: before a removal the tidy appends `<seconds> branch <name> <tip>` to `hard-eng-tidy-removed.log` in the Git common folder and drops lines older than 30 days; a write that fails keeps the item. `git branch <name> <tip>` restores a branch while the commit is unpruned.
- Idle: 24 hours, the existing rule. A worktree's HEAD reflog and the newest of the top-level entries of its folder (not `.git`) and its tracked files (submodules included; paths that a sparse checkout left out, tagged skip-worktree, are skipped; any other missing tracked path counts as use) are older than that; it gates the build folder trim; the index is not read, because a plain `git status` rewrites it; a branch's newest reflog entry is older than that; no reflog → kept. Status runs with `--no-optional-locks`, so the tidy never refreshes the index it measures.
- Checks repeat right before removal: after the GitHub answers, every local check and the checkout re-read run again as the last read, then the removal record is written and the branch goes with `git update-ref -d --no-deref refs/heads/<name> <tip>`, so a moved tip is never deleted and a symbolic ref is never followed.
- Branches: a local branch is deleted only when merged, idle, not checked out in any worktree, not named by a paused rebase or bisect, not a symbolic ref and not the target of one, without an open PR, without a stash that names it, and not `main`, `master`, `develop`, the base, origin's default branch or `hard-eng/update` (the updater owns it). A symbolic branch (`refs/heads/trunk` pointing at `refs/heads/main`) is listed with `%(symref)` and skipped, because `update-ref -d` follows it without `--no-deref`.
- Busy check: Linux reads `/proc/<pid>/cwd` and `/proc/<pid>/fd/*`; macOS runs `lsof -n -P -w -F n` once. Neither available, or a non-POSIX host → no build folder is trimmed; branches are still removed.
- Rust: in each worktree except the session's own (the primary checkout included), `target/` goes when `Cargo.toml` is at the worktree root, `target/CACHEDIR.TAG` holds cargo's signature, Git ignores `target/` and tracks nothing in it, the worktree is idle, no folder in the top two levels of `target/` changed in 24 hours, no process is inside the worktree, `target` is not a symlink, a mount point or on another device than the worktree (`tests/test_tidy_rules.py::test_tidy_keeps_a_build_folder_that_is_a_link_or_a_mount_point` for the symlink and the mount point, `tests/test_tidy_rules.py::test_a_build_folder_on_another_device_than_its_worktree_is_foreign` for the device, with a patched `st_dev`), and, as the last check, a walk of `target/` finds no nested repository, with a `.git` entry or bare (`HEAD`, `objects` and `refs` together) (a tagged `target/` can hold a repository; the walk stops at the first hit and runs only when the trim is about to act). Cargo rebuilds it.
- Remote branches: not deleted, and setup does not turn on GitHub's "automatically delete head branches". That setting needs admin rights, changes the repository for every person and tool, and GitHub's page names branch protection and repository rules as what can stop it. So an unprotected `develop` is at risk when a `develop` → `main` release PR merges. `ship cleanup` already deletes the remote task branch after a verified merge. A remote branch costs no local disk.
- Remote-tracking refs: the tidy's fetch names one branch (`fetch --no-tags origin <base>`) and prunes nothing, even with `fetch.prune` set (`tests/test_tidy_rules.py::test_the_tidy_fetch_prunes_no_remote_tracking_branch_even_with_fetch_prune_set`).
- A machine storage tool outside Hard Eng may also remove build folders. The tidy depends on no such tool; whichever runs first removes, and the other finds nothing.
- Code home: the tidy goes in `.hooks/stale_updates.py` (cleanup of what work left behind), so no new `.hooks` module adds work to each config load of an installed project. Tests go in a new `tests/test_tidy.py`, since `tests/test_update_runner.py` is at 988 lines.

## Risks + recovery

Data loss is the material risk. Recovery: every rule keeps a branch or build folder when a check cannot answer; checks repeat right before removal; branch deletion names the expected tip. A deleted local branch whose tip was merged is still on the base; its name comes back with `git branch <name> <tip>` from the log line. A removed `target/` is rebuilt by cargo. A wrong removal found later → revert the tidy call in `run_update` (one line) and fix the rule with a failing test first.


Review declined: a branch that a worktree checks out between the final checkout re-read and the `update-ref` call. The re-read runs immediately before the deletion, a branch idle for 24 hours is checked out by a person in the same Git call window only, and a deleted merged branch comes back with `git branch <name> <tip>` from the log line. `git branch -D` would drop the tip guard instead.

Review declined: unreadable processes of root and system accounts counting as unknown :: a user cannot read a root process's folder; every other guard has already passed, so the removed folder holds no work. Only a process of another person's account (user id from 1000, not ours) makes a worktree unknown, because counting every Linux system service would keep every worktree.

Review declined: a branch whose net change is zero (a commit and its revert) is removed :: its net change is zero, so the base holds everything the branch changes; the removal log file keeps its tip.

Review declined: a remote-tracking branch that was deleted on origin still counts as merged, so a later `git fetch --prune` and 30 days drop the commit :: the tidy's own fetch prunes nothing, and the rescue refs hold every commit that the base tip lacks, remote-tracking or not, for 30 days, the same as Git's own expiry of unreachable commits.
