# Remove merged, unused worktrees and branches in the session-start background run

Status: Complete

## Outcome + scope

The background run that each session start already launches also removes merged, idle worktrees and merged local branches of the same repository, and the idle Rust build folders of kept worktrees. It uses no model tokens and adds no hook time. Non-goals: remote branch deletion; a GitHub repository setting change; a new command or agent text; worktrees of other repositories; checkouts with no installed source revision (the Hard Eng source repository and installs from an uncommitted copy), because a launch there would add hook time; Windows hosts for the worktree and build folder steps.

## Decisions + authorization

Blockers: None.
Handoff: Approval
Authority: Autonomous — the user asked for a deterministic, token-free tidy at the very start of a session; design is the maintainer agent's call. This task is plan-only: commit the plan, no push, no code.

Design, settled:

- Where: `run_update`, after the update lock is released. The tidy takes its own lock, `hard-eng-tidy.lock` in the Git common folder; a held lock → no tidy this run. So `update_running` and the "still running" notes do not change. `start_update` and every hook path stay unchanged, so no hook does new work. The tidy runs when the update child fails, but not after a signal stopped the run. During the tidy, SIGTERM has its default action. A stop between two removals loses nothing: each removal is one command on an item that passed every check, and a part-removed worktree folder is cleared by `git worktree prune`.
- Time limits: every Git call 120 s, `lsof` 60 s, each gh call 60 s. One error rule: a command that fails or times out for one item (a worktree, a branch, a build folder) keeps that item, the log names the command, and the tidy goes on to the next item. A failure that concerns the whole repository (the base fetch, a listing) stops the tidy for that repository and keeps everything not yet removed.
- Report: the tidy prints one line per item, kept or removed with the reason, to the run's output, which is already `.hard-eng/update.log`. Only when it removed something, it adds one line to the result file, which the next session start already prints: `Tidy: removed N worktrees, N branches, N build folders (.hard-eng/update.log).` The line never holds the word `failed`, so the freshness and Stop notes read it as before. Nothing removed → no line, so no tokens.
- Base: `update_base` (shipping base, else origin's default branch), fetched with `fetch_base`. A failed fetch stops the tidy; the log says why.
- Merged: the head is an ancestor of `origin/<base>`; or `git merge-tree --write-tree <tip> <head>` merges cleanly into exactly the tip's tree (the base already holds every change, whitespace included; `git cherry` ignores whitespace, so it is not used). The merge runs in an empty scratch repository with the real objects as alternates, `--attr-source` set to the empty tree, no attributes file, no system or global config and no `info/attributes`, so no merge attribute or merge driver (`merge=ours`, `merge=union`) can turn a change into nothing; no single Git switch covers `info/attributes`, so the scratch repository is the switch; or a PR merged into the base has that exact head commit (`gh pr list --state merged --head <name> --base <base> --json headRefOid`, only when the Git tests fail). A PR merged into another branch never counts.
- GitHub calls: every local check (ancestor, content merge, idle, stash, log, changes, hidden edits, operation, submodule, process) runs before any gh call; gh is last. A gh answer that keeps an item is remembered in the Git common folder (`hard-eng-tidy-gh.json`) for 24 hours: no merged PR for a branch at a head, and an open PR for a branch. A missing or failed answer is not remembered. So a kept branch costs no gh call at the next session start. The tidy lock is in the same common folder, so sibling worktrees never run a tidy at once.
- Objects: `git merge-tree --write-tree` runs with a scratch object folder under the temporary folder (the repository's objects as alternates), so the tidy writes no object into any repository; the folder is removed at the end, and an abandoned one falls to the temporary-folder sweep after a day. A dry run over 123 repositories wrote 23,315 loose objects into 16 of them (20,424 in one) before this rule.
- Logs: every commit in them is checked, with a stop at the first unmerged one; a removal drops the HEAD and branch logs, so an item stays when any commit in them is neither an ancestor of the head, of the tip or of a remote branch, nor merged by content. The removal log line names the removed worktree's HEAD.
- Hidden state: a worktree stays when `git ls-files -v` shows a tag other than `H` (assume-unchanged, or a skip-worktree file that is present; a skip-worktree file that is absent is sparse and holds nothing), or its Git folder holds `rebase-merge`, `rebase-apply`, `BISECT_LOG`, `MERGE_HEAD`, `CHERRY_PICK_HEAD` or `REVERT_HEAD`. A worktree with no commit yet stays and the tidy goes on.
- Open PR: one `git ls-remote --heads origin`. A branch that is still on origin needs `gh pr list --state open --head <name> --json number` (one exact call per branch, so no page limit hides a PR); any open PR keeps it. No gh answer (missing, failed, timed out, not GitHub) → every branch still on origin is kept.
- Own Git folder: a removal deletes the worktree's private Git folder, so each entry in it is read first. Known entries hold no work: `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `COMMIT_EDITMSG`, `AUTO_MERGE`, `index`, `gitdir`, `commondir`, `config.worktree`, Hard Eng's own `hard-eng*` state, `info/exclude`, `info/sparse-checkout`. Any other entry keeps the worktree. Every ref below `refs/` and every logged ref is tested like the HEAD log (a commit merged nowhere keeps the worktree). Submodule Git folders below `modules/` (nested ones too) keep the worktree when any ref, log entry or stash commit is on no remote branch, or when they hold an unknown entry or a hook that is not a sample.
- Paused operations: a branch that `rebase-merge/head-name`, `rebase-apply/head-name` or `BISECT_START` names in any worktree counts as checked out, so a paused rebase or bisect finds its branch.
- Paths: every tidy path comparison (process path, session, Codex folder) folds letter case and Unicode form (NFC) on both sides, because a macOS volume ignores both and `lsof` may spell a path differently.
- Removal record: before a removal the tidy appends `<seconds> branch <name> <tip>` or `<seconds> worktree <path> <HEAD>` to `hard-eng-tidy-removed.log` in the Git common folder and drops lines older than 30 days; a write that fails keeps the item. `git branch <name> <tip>` restores a branch while the commit is unpruned (Git prunes after two weeks).
- Kept lines: a locked worktree and a worktree whose folder is gone each get a `kept worktree` log line.
- Idle: 24 hours, the existing rule. A worktree's HEAD reflog and the newest of the top-level entries of its folder (not `.git`) and its tracked files (submodules included; paths that a sparse checkout left out, tagged skip-worktree, are skipped; any other missing tracked path counts as use) are older than that; the index is not read, because a plain `git status` rewrites it; a branch's newest reflog entry is older than that; no reflog → kept. Status runs with `--no-optional-locks`, so the tidy never refreshes the index it measures.
- A worktree is removed only when all hold: not the session's worktree, not the primary checkout, not bare, not locked, not prunable; not inside the Codex app's worktree folder (`$CODEX_HOME/worktrees`, default `~/.codex/worktrees`), because the Codex app keeps its own record and archives its own worktrees; idle; HEAD merged; no stash whose subject names its branch or whose first parent is its HEAD; branch (if any) has no open PR; no process has its current folder or an open file inside it; status shows no change and no untracked file; ignored entries are only Hard Eng's own placements, `.hard-eng/` without a non-empty `browser/` folder, `__pycache__`, `.pytest_cache`, `.ruff_cache`, `.mypy_cache`, the `INSTALL_FOLDERS`, and a `target/` that holds cargo's `CACHEDIR.TAG`. Anything else, such as `build/`, `dist/` or `.env` files, keeps it. No recovery copies.
- Submodules: each initialized submodule must be clean, at the recorded commit, with no stash, and `git rev-list HEAD --branches --not --remotes` prints nothing in it. Then `git worktree remove --force` removes the worktree and its submodule Git folders.
- Checks repeat right before removal, as `ship cleanup` does. A branch goes with `git update-ref -d refs/heads/<name> <tip>`, so a moved tip is never deleted.
- Branches: a local branch is deleted only when merged, idle, not checked out in any worktree, without an open PR, without a stash that names it, and not `main`, `master`, `develop`, the base, origin's default branch or `hard-eng/update` (the updater owns it).
- Busy check: Linux reads `/proc/<pid>/cwd` and `/proc/<pid>/fd/*`; macOS runs `lsof -n -P -w -F n` once. Neither available, or a non-POSIX host → no worktree or build folder is removed; branches without a worktree still are.
- Rust: in each kept worktree except the session's own (the primary checkout included), `target/` goes when `Cargo.toml` is at the worktree root, `target/CACHEDIR.TAG` holds cargo's signature, Git ignores `target/` and tracks nothing in it, the worktree is idle, no folder in the top two levels of `target/` changed in 24 hours, and no process is inside the worktree. Cargo rebuilds it. A removed worktree takes its `target/` with it.
- Remote branches: not deleted, and setup does not turn on GitHub's "automatically delete head branches". That setting needs admin rights, changes the repository for every person and tool, and GitHub's page names branch protection and repository rules as what can stop it. So an unprotected `develop` is at risk when a `develop` → `main` release PR merges. `ship cleanup` already deletes the remote task branch after a verified merge. A remote branch costs no local disk.
- A machine storage tool outside Hard Eng may also remove build folders. The tidy depends on no such tool; whichever runs first removes, and the other finds nothing.
- Code home: the tidy goes in `.hooks/stale_updates.py` (cleanup of what work left behind), so no new `.hooks` module adds work to each config load of an installed project. Tests go in a new `tests/test_tidy.py`, since `tests/test_update_runner.py` is at 988 lines.

## Risks + recovery

Data loss is the material risk. Recovery: every rule keeps a worktree or branch when a check cannot answer; checks repeat right before removal; branch deletion names the expected tip. A deleted local branch whose tip was merged is still on the base; its name comes back with `git branch <name> <tip>` from the log line. A removed `target/` is rebuilt by cargo. A wrong removal found later → revert the tidy call in `run_update` (one line) and fix the rule with a failing test first.

Review declined: a worktree that switches to unmerged work between the last branch and commit comparison and the removal. The worktree must be idle for 24 hours, the comparison runs immediately before the removal, and Git offers no lock that a remover can hold against a checkout, so the window is the length of one Git call.

Review declined: a branch that a worktree checks out between the final checkout re-read and the `update-ref` call. The re-read runs immediately before the deletion, a branch idle for 24 hours is checked out by a person in the same Git call window only, and a deleted merged branch comes back with `git branch <name> <tip>` from the log line. `git branch -D` would drop the tip guard instead.

Review declined: unreadable processes of root and system accounts counting as unknown :: a user cannot read a root process's folder; every other guard has already passed, so the removed folder holds no work. Only a process of another person's account (user id from 1000, not ours) makes a worktree unknown, because counting every Linux system service would keep every worktree.

Review declined: a branch whose net change is zero (a commit and its revert) is removed :: its net change is zero, so the base holds everything the branch changes; the removal log file keeps its tip.
