# Fix the faults that the round 4 audit reproduced in normal use: dead ends as a project grows, messages that name no step or reason, and gates that live on after a stop

Status: Complete

## Outcome + scope

A project that grows after install no longer reaches a check that names no way out, and no longer gets a pass that checked nothing. A failed check, update or ship step says what failed and what to do next. A stopped check leaves no running gate. Each item was reproduced by a round 4 audit run in a sealed copy, or by the coordinator.

Non-goals:

- A raw Python error at push on a branch that has no Hard Eng files. The fix needs a new launcher text, and `is_own` in `.hooks/hook_chain.py` knows an own launcher only by its exact text. Old launchers would then count as project hooks. It needs old-text recognition first, as its own plan.
- A push snapshot that stays in the temporary folder after Ctrl-C. `sweep_temporary` in `.hooks/update_runner.py` already removes a left snapshot of the repository after 24 hours, in each background update. A second cleanup in the pre-push would copy that owner.
- A Dart or Flutter package that ignores `pubspec.lock`. Its lockfile gate passes locally and fails in each fresh checkout, with Dart's own clear reason. A setup refusal would also stop each update of a library package that follows Dart's advice.
- A second Python root package that a project adds after install. An existing Import Linter block in `pyproject.toml` does not name it, and the gate passes. The design review found it by a probe; no audit run reached it.
- A project with no `origin/<base>` ref, such as a new project before its first push. There the size count and the plan scope both read only the uncommitted work, so they agree. A stage check asked for by name then needs a plan for that work, as designed.
- A project with no shipping policy: session start still builds the update branch, and `update-pr` then stops at the missing policy. The message is true, and it now names the step.
- The 24 hour memory of a refused update. The message names the published setup command, and that command retries at once.
- `adopt` stopped by SIGTERM. A person runs it in a terminal, where Ctrl-C already stops its gates.
- Choices for the maintainer: debt lines that hold source context, Dart `example/` in coverage, the move to Bun for npm, pnpm and yarn projects, a deleted skill that an update brings back, one committed scaffold edit that blocks each update, a new review after a rebase, a review record with findings that passes ship, the coordinator lease time, a stricter wait rule for `for` loops, the basic mode pass line, the Dart dead-code entry point, the Swift file length rule, a `Gap:` line for a second language, the Trello title checks in `new` and `update --name`, a two-day wait for the mise launcher, and whether `e2e/`, `cypress/` and `.storybook/` folders and `*.cy.ts` files hold test-only code for the sources guard.
- A Stop or a push on the default branch, where the caller gives a base. `released_plans` keeps the local default branch tip as a release tip there, because the push check gives the exact remote base and relies on it (Decided 9).
- Rare cases that no run reached in normal use: a sign-in prompt through `GIT_ASKPASS` in a background update, a fix worktree left after a merged update, a workflow generated before 2026-09-10 that migrates into one that fails actionlint, a cut-off session state file, Python tests in `test/`, an instruction file inside an ignored `venv/` folder, the size reason after commits on a local default branch with no remote, submodule reuse from a local path, and a failing XCTest with no reason.
- A missing package script that fails only its own gate. The message now names the package, gate and script; the validation still stops the check, as it does for each wrong gate file.
- The mutation report wording for lines that no test runs.
- The cost of the file scans at session start. In-process on about 2,000 files, `repository_files` takes about 35 ms, `package_manifests` 18 ms and `has_workflows` 7 ms, the same before and after this round. A speed pass needs its own plan, with proof of equal results.
- A project file that does not parse. A `pubspec.yaml` with a syntax error stops session start and `check` with a raw traceback, in the released code too. The probe of the session start line found it. The same cause needs a search of each manifest read, so it is the first item of the next round.
- `check` with no network. The tool lookup then fails with the raw command error, which names no reason. The hand probe found it; no audit run did.

## Decisions + authorization

Blockers: None.
Handoff: Approval
Authority: Autonomous. On 2026-11-10 the maintainer told the builder to run the audit and fix rounds autonomously and to follow Hard Eng and Learn.
Decided (1): setup still writes no `imports` gate while no Python package has a module; `tests/test_setup.py::test_standalone_python_does_not_invent_import_architecture` pins that. When the first module comes, the "missing mandatory checks" message for `imports` holds the whole step: the template gate with the command that setup gives it, and the Import Linter block from `import_configuration`. The first design printed the block only after the gate failed. The hand probe showed that the gate copied from the template could not start ("No such file or directory: 'lint-imports'"), because setup wraps that command in `uv run`. The step is built only when the gate is missing, so a project that has the gate pays nothing. Session start shows the first line of a gate error and points to `check` for the rest; before, it joined all lines into one, which broke the block for a copy. A design that keeps the gate from the start was dropped: it needs a new pass in the runner, a change of the pinned test and a gate migration in setup.
Decided (2): the "missing mandatory checks" message names the next step for every role: add a gate for each role to that group in `hard-eng.gates.json`, from the language template for a package role or from the gates reference for a shared role. The gates reference gains the commands of the shared roles. A setup rerun is not named, because the published setup command builds from the remote base, which does not hold the new file yet.
Decided (3): Hard Eng's own hook launchers do not make the `shell` role mandatory, and setup does not list them in a new shell gate. The listed shell script check already leaves them out (`tests/test_deployment_and_shell_gates.py::test_own_hook_launcher_needs_no_shellcheck_entry`). A first install into a Husky project then loads with no shell gate, where it stopped before.
Decided (4): a gates file with no package and no supported manifest takes an early return in `validate_required_checks`. Basic mode projects and gates files with only ad-hoc groups take it. Before that return, the check now requires the roles that a file brings: `shell` for a project shell script, `workflows` and `ci-security` for a workflow, and `deployment` for a deployment file. It also runs the listed shell script check. A gate that names its tool and has no role field still counts, as today. The secret scan roles do not become mandatory there. A `shell`, `workflows` or `ci-security` gate there must now name its tool, as in a package project, so a command such as `true` cannot fill the role. These checks run in `check` and not at session start, where they made the start 11 to 15 ms slower (Decided 15).
Decided (5): one sources guard covers Python, JavaScript and Dart. This reverses a round 3 non-goal: an audit run got "100%" line coverage with 4 of 46 lines hit in a new folder. An installed project with code outside its `sources` must list the folder or file; the message names it. A top-level tool configuration file added after install counts, as one present at install does. The guard ships as its own commit. The message also says that tests must then cover the listed files, and where test-only code belongs. For JavaScript and Dart the guard runs in `check` and not at session start (Decided 15).
Decided (6): `HE-` IDs may have one part, so a one-part registry entry such as `HE-YAGNI` is checked like each other entry. An unknown one-part token is not reported, because the code review found that a codec name in project code has that shape. An unknown ID of two parts or more is still reported. `REQ-` IDs keep two parts or more, so a ticket key such as `REQ-123` in a project's Markdown stays out of the check. A heading in a registry file that starts with `HE-` or `REQ-` and is not a valid ID is an error that names it. The requirements intro states the format.
Decided (7): a debt line and a current line are equal when the word after a count differs only in its ending for one or many: "error" and "errors", "fix" and "fixes". The neutral form drops a final "s", then a final "e", from that word. `judge` and the adopt shrink use it. The shrink keeps the recorded spelling of a line that is still there, so `require_shrink` sees no new line and the debt file keeps its format. No adopted project needs a new `adopt` run.
Decided (8): the `check` command turns SIGTERM and SIGHUP into the interrupt that already stops its gate groups. It sets the two handlers once, in the `check` branch of the command entry, as `pre_push` does in its own command. It swaps no handler back and masks no signal, which was the reverted design. A SIGHUP that the process got as ignored stays ignored, so a `nohup` run lives on. Its test runs `check` as its own process.
Decided (9): with `origin/<base>` present and no base from the caller, the local default branch tip is not a release tip in `released_plans`. A caller that gives a base keeps the old result: the join showed that the push check, which gives the exact remote base, then read an old plan as unreleased. The size count already reads the branch from `origin/<base>`; the plan scope now reads the same commits. A plan in an unpushed commit on the default branch then covers a later fix. A task branch checked against a local default branch that is ahead of `origin/<base>` changes too: the unpushed plan covers it.
Decided (10): a passing quick check prints "Hard Eng: quick checks passed; the full check runs the tests and the other gates." where it printed the ready-for-ship line. The full check keeps its line. The Stop hook relays any stage line by its shape.
Decided (11): a failed React Doctor, Fallow or secret scan gate prints its findings from the report, at most 20: file, line where the report has one, rule and message. The secret scan never prints the secret; its test builds the fake token at run time. Each line starts with the gate name and gives the place as `file:line`. A last line gives the count of the findings that are not shown and the report file. Fallow also names each copy of copied code by file and lines, never the code, and its audit report shape is read too. A secret in the history names its commit. The readers were checked against real reports of each tool, made on 2026-11-10.
Decided (12): `ship --stage ready` reads the required checks before it judges a state that is not clean, so a pending or failed check is the reason given.
Decided (13): the cleanup guard does not count what `link_local_files` put in a worktree: a link into the main checkout, and its copy of an ignored hooks folder. Git lists each file of a Husky folder that ignores itself, so the guard compares each path of the copied folder with the same path in the main checkout. A file or a link that the main checkout does not hold with the same content stops the cleanup, and the message names up to three paths. Any other ignored file still stops it too. If the main checkout wrote its hooks folder again with other content, as a Husky update does, the cleanup of an older worktree also stops. The person then removes the named files from that worktree and runs the cleanup again.
Decided (14): `update-pr` exits 1 after a remembered refusal and does not print "Nothing to publish". The Stop note reads the local `origin/<base>` ref, with no network call, and says to pull or rebase when the update is already there. A setup rerun records its result in `locked_update` in `.hooks/update_runner.py`, so `setup.py` does not change for it. A refused rerun records its own reason over an older failure. The note uses one Git process: it asks for the revision on the update branch and, only when an update waits, for the revision on the base, whose name it then reads from the gates file. A waiting update adds no Git start to Stop, and the usual Stop reads no more than before.
Decided (15): new validation runs in the session start path only when a timing run shows no slower median. If a median grows, that check moves to `check` only. Result: on about 2,000 files the role checks of a no-package project made the start 11 to 15 ms slower, and the JavaScript and Dart guard 17 to 26 ms slower. Both run in `check` only. Session start keeps the Python guard, as before. It can then say "Gates: ok." where `check` reports unlisted JavaScript or Dart code, or a missing role in a no-package project.

## Risks + recovery

- An installed JavaScript or Dart project with code in a top-level folder or file that `sources` does not list fails `check` after the update, until it lists it and its tests cover it. The message names it and the step. The update PR of such a project shows the failure before the merge. Recovery: revert the guard's own commit.
- A gates file with no package, in a project that added a shell script, a workflow or a deployment file after install, fails `check` after the update, until it has the gate. The message names the step. A gate there with the role `shell`, `workflows` or `ci-security` and a command that does not name the role's tool also fails; the message names the tool.
- A registry heading such as `## REQ-1` in a project's `docs/requirements.md` becomes an error that names the format.
- These three changes can turn an installed project red after the update. The PR text and the release text name all three with their steps.
- A one-part `HE-` token that is not a rule, such as a codec name, is not reported (Decided 6). A mistyped one-part ID in project text is then not reported either.
- Two debt lines that differ only in the ending of the count word now count as one line. No tool in the probe prints such a pair.
- A hooks folder that the main checkout wrote again with other content stops the cleanup of an older worktree, with no work at stake (Decided 13). The message names the paths.
- Uncertainty: a new check in the validation can slow session start. Cheapest check: time the real hook command, old against new, with compiled modules, 40 alternating runs, medians. The fixtures are a Flutter scaffold, a Next.js scaffold and a basic mode project with about 2,000 files, 200 of them with no suffix. If a median grows, that check moves to `check` only (Decided 15).
- Uncertainty: the host may stop `check` with a signal other than SIGTERM or SIGHUP. Then its gates still live on, as today.
- After Ctrl-C at a push through the Python launcher, the pre-push sends SIGTERM to its `check` before the launcher kills the pre-push. If the kill comes first, the gates run to their end, as today.
- Old Complete plans name tests in files that this round does not rename. No test is removed.
- Recovery for any slice: revert its commit.
