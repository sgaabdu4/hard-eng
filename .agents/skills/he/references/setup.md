# Setup and integration

- Deployment discovery = setup adds the native Trivy deployment check described in [Gates](gates.md) when Git-visible files include `Dockerfile`, `Containerfile`, `Chart.yaml`, `tfplan`, or `.tf`/`.tf.json`/`.tfvars`/`.tfplan` suffixes. It scans the root, runs serially and uses the existing strict report reader. Existing shared deployment checks/direct `trivy config` commands are preserved, including their settings; they are not certified by preservation. Review Kubernetes, CloudFormation, ARM, custom Dockerfile names and other infrastructure inputs explicitly and add the same check when applicable: arbitrary YAML/JSON alone is not an automatic trigger. Provision Trivy separately and review native scope/ignores. Setup does not remove a check when its original trigger disappears.

- Shell helpers = setup adds a shared `shell` check with direct `shellcheck -- FILE...` arguments for Git-visible `.sh`/`.bash` files and extensionless helpers with a Bash/sh shebang. Ignored, deleted and symlink files are omitted. Existing shared shell checks/direct ShellCheck commands are preserved. Provision ShellCheck through the project's tool setup; retain native failure exits for findings and input errors. Maintain the explicit file list when helpers are added, renamed or removed, and review sourced files and exclusions. A `.sh` extension alone does not identify the dialect: retain a shebang or native shell directive instead of forcing Bash globally. This setup does not certify other shell dialects or embedded CI scripts.

- Entry = the current scaffold runner is `python3 .hooks/hard-eng.py check`; source installation uses `python3 setup.py TARGET`. Use additional session/CI entrypoints only when present and verified; a missing command is incomplete setup, not a passing check.
- Install = from the target project root, run `curl -fsSL https://raw.githubusercontent.com/sgaabdu4/hard-eng/main/setup.sh | sh`. The installer copies shared files into the project; it adds no Git submodule. Codex and Copilot read `.agents/skills` directly. Only Claude receives links in `.claude/skills`. Preserve existing project instructions, skills and configuration.
- Installation templates = adapt [Python](../templates/hard-eng.python.json), [JavaScript/TypeScript](../templates/hard-eng.javascript.json) or [Dart/Flutter](../templates/hard-eng.dart.json) into root hard-eng.gates.json; retain the actual package manager, test runner, source boundaries and stricter settings. Configure full production coverage, Python strict typing/import contracts and relevant React/build checks. Combine package entries for monorepos with explicit dependencies. Templates are starting points, not proof of working gates.
- CI = setup installs the bundled `hard-eng` workflow with detected SDKs and locked dependency setup. It runs the shared runner for the pushed/PR commit. Require the `hard-eng` job in branch protection only when authorized; local workflow validation does not prove a remote run or protected-branch enforcement.
- Workflow validation = setup adds a shared `workflows` check running `actionlint -no-color` when `.github/workflows` contains a `.yml` or `.yaml` file. Existing shared workflow checks or direct Actionlint commands are preserved without duplication; an existing check is not certified merely by preserving it. Setup does not remove existing checks when workflows disappear. Provision Actionlint through the project's tool setup. Its optional ShellCheck/Pyflakes integrations need their executables available; built-in workflow validation does not prove embedded-script analysis or remote CI enforcement.
- Workflow security = the same detection adds a separate `ci-security` check running `zizmor --strict-collection --persona=auditor --format=plain .`. Existing shared security checks/direct Zizmor commands remain unchanged. Strict collection rejects malformed inputs instead of skipping them; auditor mode surfaces all personas, including informational findings and potential false positives. Resolve findings or apply narrowly evidenced native exceptions, including any needed for agreed automatic tool updates; add no blanket exception. Retain native failure exit codes and normal credential-based online audit selection. Offline fixtures verify only offline audits; provision the tool and online access separately before claiming full coverage.
- Fresh checkouts = `lockfiles` checks run first and must prepare locked dependencies with the existing package manager, such as `uv sync --locked`, `npm ci` or `flutter pub get --enforce-lockfile`. CI installs SDKs; the shared runner owns this dependency step so pre-push and CI use the same setup.

- Native tools = the runner uses uvx for standalone Python tools and npm-provided mise for the latest native/JavaScript scanners. Native caches live under the operating system's temporary directory or package manager's own cache; no global activation or gate-result cache is added. npm and uv must be available; Dart Decimate additionally requires Cargo and is installed from its current upstream Git revision. Version-resolution failures fail provisioning. Authenticated GitHub API access avoids anonymous release-list rate limits. Python tests, deptry and Import Linter use native uv tool overlays over the prepared uv/Poetry project environment, upgrading tool packages without changing the project lockfile.
- Service readiness = session start detects Sentry/Appwrite SDK imports in supported production source and asks the active agent to verify the configured service project with a read-only MCP call. Missing service configuration or credentials remains a reported readiness gap; setup does not invent an Appwrite endpoint or grant account access.
- Native hook proof = Claude and Copilot completion blocking and bounded retry were exercised locally. Codex hooks executed when supplied as reviewed per-invocation definitions, but native discovery of newly installed project configuration was not established. Review/trust activation in the target client remains an acceptance prerequisite; do not claim all three clients are activated solely from configuration files.
