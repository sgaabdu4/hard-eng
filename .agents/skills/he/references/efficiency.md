# Deterministic efficiency checks

Apply this reference only to a changed bulk, async or performance-sensitive flow. First identify the real contract from code, tests and applicable service limits. Do not invent a numeric limit to make a test deterministic.

## Pass/fail contract

Before claiming the affected flow is verified, use its existing test runner to assert the relevant outcomes below. Prefer controlled inputs, fake clocks or synchronization primitives over sleep-based timing comparisons. Reuse or extend the current tests; name the test and command in the normal completion report. Put required tests in the existing gate command so local checks, pre-push and CI run them where those integrations are configured. A prose review, an unrun test or an exit-zero command that skips the required case is not proof.

| Changed flow | Deterministic assertion |
| --- | --- |
| Batches/chunks | For input size n and the actual item limit b, exercise empty input, b-1, b and b+1 where meaningful. Assert the exact resulting records, required order and no missing/duplicate output. Where only the item limit applies, assert ceil(n/b) calls; account explicitly for payload limits and retries when they change that count. |
| Fan-out/queue | Hold workers at a controlled boundary and verify active work never exceeds the configured cap and pending work obeys its bound or rejection policy. Release capacity and assert completion, error propagation and relevant cancellation/timeout cleanup; waiting for a short wall-clock duration alone is not a worker-limit test. |
| Repeated I/O | Assert the required query/request count for representative input sizes and cache states. Include relevant partial failures and retry limits so retries cannot silently duplicate effects or amplify overload. |
| Hot-path scaling | Assert an independently justified operation-count bound for named input dimensions where feasible. Keep time/space complexity reasoning explicit; neither a few timing samples nor a complexity lint proves general Big-O. |

If the necessary contract is unknown, identify the missing limit or behavior and keep that outcome unverified. Do not mark a project performance gate complete from these instructions alone. Runtime latency/memory budgets need an actual requirement and a representative measurement environment; they remain measurements, not universally deterministic assertions.

## Native checks and implementation choices

- Performance/async rules = the existing Python annotation command also selects Ruff RUF017 (quadratic list summation) and ASYNC210 (blocking HTTP in async functions); the existing Biome typing-lint command also selects noAccumulatingSpread, with warnings failing. Dart setup and configuration validation require unawaited_futures alongside its existing analyzer rules; explicit intentional `unawaited` remains valid. Keep these batched native checks and the full project lint command. They catch specific patterns within the scanned scope, not general Big-O or runtime performance. Do not globally enable synchronous-I/O recommendations or experimental promise rules without project evidence.
- Bulk operations = when changing a real bulk flow, reuse native batching, pagination or streams and choose chunk sizes from the service's item/payload/rate limits. Preserve required ordering and test relevant empty, exact-boundary and final-partial-chunk cases, with no lost or duplicated records. Verify partial failures and retry behavior, and meaningful request/query counts to catch repeated per-item I/O. Reuse existing tests; do not add batching or a queue service to a flow that does not need it.
- Async work = when changing fan-out or background processing, bound both active work and pending work, define what happens when capacity is full, and preserve error propagation, cancellation and timeouts. Check cleanup and retries where they affect that flow. A semaphore around an eagerly created task for every input does not bound pending-task memory. Parallelize only independent work; preserve dependency order and account for native workers, connections and memory. Do not replace every sequential await with Promise.all, asyncio.gather or Future.wait, or assume async makes CPU work parallel.
- Scaling = for changed performance-sensitive paths, name the input dimensions and expected time/space growth; inspect repeated scans, copies, sorts and I/O. Reuse tests to verify relevant operation/query counts or representative scaling, including skewed inputs where applicable. Measure latency or memory against a real requirement on a representative environment before adding a budget; avoid noisy universal timing thresholds. Complexity lints and timing samples do not prove general Big-O. Do not ban nested loops or add benchmark infrastructure without a demonstrated need; explain relevant findings in the normal change report, not a new tracking file.
