# Repository-grounded UX reference

Apply to visible changes, including small ones; scale the preview to the change.

- Before creating a proposal = inspect the current screen + affected flow/states and actual token/theme/component/layout owners. Use `DESIGN.md` + production code; contradictions or unavailable relevant UI → expose the gap and resolve it before presenting a design as grounded. Genuinely new surface → inspect the nearest existing flow and explain the gap.
- Existing surface = capture the unmodified starting app at its actual route/screen first. Render the proposal through that same screen tree in an isolated checkout. Preserve surrounding navigation, layout and unaffected controls. Reusing production atoms/cards inside a reconstructed page does not establish screen fidelity. A crop may focus on the affected state after inspecting its actual screen context.
- Preview = use the existing app runner and browser/device facilities; no production implementation while planning. Supply synthetic data at the existing data boundary, preserving the UI tree. Assert the actual route/screen and expected state before capture; keep the native run result and relevant trace when available. Do not replace the document, assemble explanation panels, or add diagnostic banners to a claimed baseline. Label synthetic/proposed states and explain the issue in the conversation, outside the captured UI. No mandatory video or additional visual-testing platform.
- New surface = repository components/tokens first. A generated image or standalone concept is allowed after nearest-flow inspection and an explicit new-surface reason. If no project/UI/design exists, use the user's brief + supplied assets, state that absence and label design assumptions; the result is a concept, not an existing-app capture. A missing design document alone is not this exception: inspect the actual UI/code. Generated bitmap assets may be explored for existing surfaces, but judge them inside the real screen.
- Image concepts = when a bitmap materially helps, load the installed `imagegen` skill. With Codex CLI available, use a bounded `codex exec` request in the isolated preview workspace: ask it to use that skill, provide the brief, constraints, reference-image roles and output location, then retrieve, inspect and show the selected image. Otherwise use the host's available imagegen capability. Keep generation modes, API fallback and asset handling with that skill; no custom runner or automatic installation. Use HTML/CSS or existing vector owners when they are sufficient.
- Review = use [E2E](../../e2e/SKILL.md) to inspect baseline and proposal against the actual screen, source owners and capture procedure, then compare affected states/devices. Confirm that only the intended change differs; reject fabricated baselines and explanatory panels even if they compile or pass overflow/pixel checks. Start with the smallest representative pair before expanding states. Display each proposed delivery image in the conversation; a file path, unopened URL or uninspected image is insufficient.
- `ux_reference` = use the existing plan template's `Surface`, `Before`, `Proposed`, `Capture` and `Review` fields alongside Result/Evidence. Surface names the route/screen and production owner; Capture records starting revision, native command/browser/device actions, route/state assertions and actual result; Review records the inspected comparison, affected devices and settled direction. Existing screens require both images. New screens in an existing app use the nearest existing flow as the baseline; only a new app with no prior UI may explain an absent baseline. Link existing artifacts; no sidecar receipts or hashes. Gate validation enforces declarations, not image authenticity or design quality; the native capture and visual inspection cannot be replaced by a Passed label.
- User changes direction → update the same preview, refresh, inspect and show the matching capture. Superseded media cannot establish readiness. Reuse previously inspected evidence only while it still represents the current UI and proposed change.
- Build verification = compare the actual implementation against the accepted reference on the affected surface; repair unexplained visual differences. A planning preview does not prove the implemented journey works.
